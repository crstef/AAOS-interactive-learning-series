Step 1 — Environment

Getting 25 GB of toolchain onto a full machine

The development laptop — Windows 11, Intel i5, 20 GB RAM — had almost no space left on C:. An AAOS setup needs roughly 20–25 GB, and essentially all of it defaults to the system drive.

1Variables first, install second

Every Android tool decides where to write at first run. Set these after installing and you get a split installation the SDK manager cannot reconcile.

ANDROID_HOMED:\Android\Sdk
ANDROID_SDK_ROOTD:\Android\Sdk
ANDROID_USER_HOMED:\Android\.android
ANDROID_AVD_HOMED:\Android\.android\avd
GRADLE_USER_HOMED:\Android\.gradle
JAVA_HOMED:\Android\jdk\jdk-17…

2CPU virtualisation

The automotive emulator is an x86_64 VM. Without hardware acceleration it does boot — slowly enough to look like a hang rather than an error.

# enable VT-x / AMD-V in BIOS, or turn on
# the Windows Hypervisor Platform feature

emulator.exe -accel-check

This is the one step that cannot be scripted, because it lives in firmware. Check it first — every later problem is easier to diagnose once acceleration is known good.

ANDROID_AVD_HOME matters most. Without it the emulator's 7 GB data partition and its snapshots land back on C:, regardless of where the SDK itself was installed.
Step 2 — Emulator

The automotive virtual device

A phone AVD will install this APK and run it happily — and then never deliver a single vehicle property, with no error to explain why.

1AVD as configured

System imageandroid-33 · automotive · x86_64
Screen1024 × 768 · density 160
RAM / VM heap3072 MB / 512 MB
CPU cores4
Data partition7000 MB
GPUenabled · auto

3072 MB is a deliberate compromise: the automotive image is heavier than a phone image, but Android Studio and Gradle need their share of 20 GB too.

2Where android.car.jar comes from

Not the standard SDK, and not the system image — the image is what the emulator runs, and contributes nothing to the compile classpath. It ships inside the installed platform:

Sdk/platforms/android-34/optional/
        └── android.car.jar

Registered there as android.car, which is exactly the name Gradle resolves:

android {
    compileSdk = 34
    useLibrary("android.car")
}
Confirm the image really is automotive before debugging anything else — adb shell pm list features | findstr automotive should return feature:android.hardware.type.automotive.
Step 3 — Architecture

From a vehicle signal to a redrawn pixel

Five Kotlin source files. Only one of them imports android.car — the dashboard itself knows nothing about the Car API, which is why it renders in an Android Studio preview with no emulator at all.

MainActivity.kt

Requests runtime permissions, then connects. Hosts the Compose tree.

VehicleDashboard​ViewModel.kt

The only file importing android.car. Connects, subscribes, converts.

VehicleUiState.kt

Immutable snapshot of everything displayed. Defaults to "--", never 0.

DashboardScreen.kt

Gauge, sparkline, gear row, meters, cards. No vehicle logic.

Step 4 — Car API

Connect, subscribe, receive

1Connecting

car = Car.createCar(getApplication())
cpm = car?.getCarManager(Car.PROPERTY_SERVICE)
          as? CarPropertyManager

if (cpm == null) {
    Log.e(TAG, "CarPropertyManager unavailable")
    return
}

The as? is doing real work. On a non-automotive image getCarManager returns null, and a hard cast would throw before any error handling could run.

2Subscribing

for (p in liveProps) {
    try {
        cpm?.registerCallback(callback, p,
            CarPropertyManager.SENSOR_RATE_ONCHANGE)
    } catch (e: Exception) {
        Log.w(TAG, "register failed for $p", e)
    }
}

SENSOR_RATE_ONCHANGE means the platform pushes on change rather than at a fixed rate — an idle vehicle costs nothing. Each property is guarded individually so one unsupported ID cannot cost you the other five.

3Receiving — one callback, dispatched on property ID

override fun onChangeEvent(value: CarPropertyValue<*>) {
    val num = asFloat(value.value)
    when (value.propertyId) {

        VehiclePropertyIds.PERF_VEHICLE_SPEED -> {
            val mph     = ((num ?: 0f) * 2.23694f).roundToInt()      // m/s → MPH
            val history = (uiState.speedHistory + mph).takeLast(40)  // the whole "speed graph" feature
            uiState = uiState.copy(speedMph = mph, speedText = mph.toString(), speedHistory = history)
        }

        VehiclePropertyIds.GEAR_SELECTION -> {
            val g = (value.value as? Int) ?: 0
            uiState = uiState.copy(gearRaw = g, gearText = gearLabel(g))
        }
        // … fuel, battery, range, odometer
    }
}
Step 5 — Properties

The API returns raw machine values

Every single one needs work before a driver can read it. Metres per second, millilitres, bit constants — none of it is displayable as it arrives.

1Gear is a bit flag, not a number

The values are not sequential and cannot be compared as magnitudes. Park is 0x4; Drive is 0x8.

val gears = listOf(0x0004 to "P", 0x0002 to "R",
                    0x0001 to "N", 0x0008 to "D")

Ordered P R N D for the driver, not numerically. The raw int is kept in state so the row highlights by exact match rather than by parsing a label.

2Millilitres are meaningless alone

15000 tells a driver nothing without the tank size — so INFO_FUEL_CAPACITY is read at connect and cached.

val pct = if (fuelCapacityMl > 0f)
    ((ml / fuelCapacityMl) * 100f).roundToInt().coerceIn(0, 100)
else -1                          // sentinel: capacity unknown

val low = if (pct >= 0) pct < 15 else ml < 5000f

Even the low-fuel threshold degrades gracefully — 15 % when capacity is known, an absolute 5000 ml when it is not.

Step 6 — Permissions

Declaring a car permission is not enough

This is the single most common way to lose an afternoon on AAOS. Four of the five permissions here are dangerous, which means they must also be requested at runtime — or every read throws SecurityException.

1Declared in the manifest

<uses-permission android:name=
    "android.car.permission.CAR_INFO" />        ← normal
<uses-permission android:name=
    "android.car.permission.CAR_SPEED" />       ← dangerous
<uses-permission android:name=
    "android.car.permission.CAR_POWERTRAIN" />  ← dangerous
<uses-permission android:name=
    "android.car.permission.CAR_ENERGY" />      ← dangerous
<uses-permission android:name=
    "android.car.permission.CAR_MILEAGE" />     ← dangerous

2And requested at runtime

private val permissionLauncher =
    registerForActivityResult(
        ActivityResultContracts.RequestMultiplePermissions()
    ) {
        viewModel.connect()
    }

if (hasAllPermissions()) viewModel.connect()
else permissionLauncher.launch(requiredPermissions)

connect() runs from the result callback regardless of the answer. A partial grant should still produce a partly-working dashboard — granted properties work, the rest show --.

3Which permission unlocks what

CAR_INFOINFO_MAKE / MODEL / YEAR / FUEL_CAPACITY
CAR_SPEEDPERF_VEHICLE_SPEED
CAR_POWERTRAINGEAR_SELECTION
CAR_ENERGYFUEL_LEVEL · EV_BATTERY_LEVEL · RANGE_REMAINING
CAR_MILEAGEPERF_ODOMETER

4Usable while driving

An app that does not declare itself distraction-optimised is blocked the moment the vehicle moves — exactly when a dashboard is most useful. This is a read-only display requiring no interaction, so it qualifies:

<meta-data
    android:name="distractionOptimized"
    android:value="true" />
Step 7 — Limits

What the platform will not give you

The brief lists engine RPM, engine temperature and door status among the signals to fetch. They are not on the dashboard — and no amount of manifest declaration or user consent would change that.

SignalPropertyPermission requiredProtection level
Engine RPMENGINE_RPMCAR_ENGINE_DETAILEDsignature|privileged
Coolant temperatureENGINE_COOLANT_TEMPCAR_ENGINE_DETAILEDsignature|privileged
Oil temperatureENGINE_OIL_TEMPCAR_ENGINE_DETAILEDsignature|privileged
Door open / lockDOOR_POS · DOOR_LOCKCONTROL_CAR_DOORSsignature|privileged
SpeedPERF_VEHICLE_SPEEDCAR_SPEEDdangerous — grantable
GearGEAR_SELECTIONCAR_POWERTRAINdangerous — grantable
Fuel / battery / rangeFUEL_LEVEL …CAR_ENERGYdangerous — grantable

1Why that word decides everything

A signature|privileged permission is granted only to an app signed with the platform key, or installed into /system/priv-app and allow-listed there. Neither is available to an app installed with adb install. pm grant does not help either — it only operates on dangerous runtime permissions and returns an error for these.

2So it shows --, not 0

Every text field in VehicleUiState defaults to "--". A zero on a dashboard is a reading; a dash is an absence. Conflating the two is how a driver ends up trusting a gauge that was never connected.

Property access is a three-way gate. Does the HAL provide it · does a permission exist at a level this app can hold · has the user granted it. Most time lost to "why is my property null" comes from assuming the first gate is the only one.
